# 用日常 Intent 记录建设回归 Script

这份样例验证的工作流是：Agent 用 Intent 进行日常操作和测试；从有业务结果的执行记录中提炼场景；Agent 编写、调试并冻结 Script；后续持续运行 Script，重新采集证据和判断业务结果。Intent 和 Script 共享设备能力与证据契约，各自维护独立运行时。

## 一条记录何时可以成为回归场景

至少记录目标 App、设备、构建标识、前置数据、操作意图、实际观察、选择器、动作回执，以及独立的业务结果。例如输入笔记后，编辑器显示、返回重开、强停后的数据库正文应一致。失败或证据不足的日常记录同样保留，但应先理解并修复问题，不能直接作为成功模板。

本次真实样例已经发现一个这种记录才能揭露的问题：SDK 曾直接调用自定义输入框的 `setText`，页面能显示文字，App 的业务监听器却未收到输入，数据库仍为空。改用真实 IME 输入连接后，中文、多行和符号内容才完成持久化闭环。

## 场景成为 Script 时保留什么

- 固定业务意图和预期结果，给测试数据使用本轮唯一标记。
- 优先使用当前观察中唯一、可操作的语义选择器，并保留定位失败的证据。
- 将页面就绪、业务状态变化写成有截止时间的观察条件。
- 将操作后的截图、树、事件和数据库／服务端结果绑定本轮 runId、App 构建与场景 ID。
- 在来源索引中引用实际 Intent 执行和证据文件；这只是编写来源，本轮判定必须使用新证据。

不需要先建设自动 Intent→Script 编译器。先让 Agent 能稳定地从实际记录编写可复跑的 Script，再根据反复出现的人工整理成本决定是否自动提炼场景。

## 计时和完成度

Script 省去逐步等待 Agent 判断和调度的成本，适合已经跑通且预期固定的重复回归。业务网络等待、页面渲染、安装重启和采集证据仍有实际成本。这里将 5～10 分钟作为冻结套件的测量目标：回归计时包含套件内必要的操作、等待、采证和独立判定；建设、调试、构建和安装另列。

必须同时报告覆盖的功能、正常／异常／重启分支、未运行项、成功率、耗时和发现的缺陷。NotallyX 全清单为 51 个功能、143 组场景模板、396 个展开覆盖槽；核心套件只是其中一部分。不能将核心场景的耗时扩称全 App 耗时。

## 扩展到整机

先为每个 App 建立这样的套件，再添加系统设置、权限、后台恢复、跨 App 分享和硬件链路。整机回归还要固定系统版本、账号、设备状态、外设与网络条件。已有的 App 套件可以组合复用；跨 App 的结果仍须有自己的独立验证，不能仅靠每个子脚本执行完成推断。

当前建设状态及实际证据见 `测试进度.md`；运行结果应以带构建和 runId 的报告为准。
