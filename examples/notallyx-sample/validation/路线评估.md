# Intent 日常工作与 Script 回归：当前判断

本次验证基于真实 NotallyX 源码、隔离 Android 安装包；早期设备为 `b46093e6`，换机续测使用 OPPO `FYZLAU49X8OVQGJ7`。上游固定在 [03ff809](https://github.com/Crustack/NotallyX/tree/03ff809f058dbcabd5f0d20f114546686dfc9cb5)，没有把演示页面当成完整业务 App。

**建议继续这条路线：让 Agent 通过 Intent 完成日常工作，积累可追溯的业务证据；再由 Agent 编写并冻结 Script，承担重复回归。当前已进入真实业务验证阶段，尚未达到整个 App 或整机的发布验收。**

## 现在已经成立的部分

1. 日常 Intent 可以驱动真实原生 App。已验证中文、多行和特殊字符输入、保存重开、标签/颜色/置顶、清单父子层级、复制后独立修改、搜索、归档恢复和回收站恢复。每个结论有自己的范围，不能合并推断全部功能通过。
2. 真实架构迁移已落地。18 个外部 DB/DAO 消费者迁入应用服务，数据库句柄生命周期、复合事务和存储维护有明确边界；Room schema 11 与业务数据格式保留。App 测试从 178 项增加到 194 项，全部通过。具体边界和仍保留的 Android 依赖见 `application-migration.md`。
3. 原数据原地升级已有证明。覆盖安装前后的 4 条业务记录、标签、偏好及文件 canonical 比较无差异；后续操作在迁移包上完成。这证明本轮数据和路径，不替代备份、加密或断电恢复验收。
4. Intent 记录已被用来编写实际 Node Script。首次成功的固定文字与组织流程回归为 **32.258 秒**，包含 APK 核对、页面等待、截图/树、强停重开、数据库采集和独立判定；11 个页面检查点有本轮新证据。该版本只完整通过 2 个场景模板，另外 3 个模板仅覆盖子流程，完整报告仍为未通过。
5. 扩展并冻结后的相同套件已三轮通过：迁移版 **73.535 秒**、原架构 **75.159 秒**、迁移版复跑 **83.762 秒**。每轮 27 个页面检查点、8 份数据库快照，完整通过文字与清单的 4 个模板，3 个组织模板仍部分覆盖。三轮初始 8 条笔记、Script/Host/场景 hash 相同，原有数据均保留。详见 `固定回归结果.md`；这不是 Intent vs Script 加速倍数，也不是长期稳定性统计。

## 这轮实际发现了什么

- 自定义输入框调用 `setText` 会绕过 App 业务监听器，出现页面有字而数据库为空。SDK 改用 IME 输入连接，实际保存重开和独立数据库读取已通过。
- Script 的快速执行暴露了键盘导致弹窗移位的竞态。脚本增加了连续新观察下的页面和目标位置稳定条件，并检查保存后真实出现的标签复选框。
- 相同正文可以出现在多张卡片。回归必须把标题、正文和标签绑定到同一张笔记卡片；全局文本匹配会产生误报或漏报。
- 证据必须核对 Host 实际发行记录、图片字节与本轮操作时间。Script 自己提交的 `passed`、一个路径或自行计算的 hash 都不足以证明业务正确。
- 冷启动时观察字段未就绪，暴露了 Host 在计算 checksum 后才将 `undefined` 归一化为 `null` 的缺陷。观察记录和动作回执都需要统一修正顺序；历史原始文件保留，不重写成新的成功证据。修复与复验结果以 `测试进度.md` 为准。
- 已完成清单项会进入只读分组，不能继续要求它可编辑。本轮原生树尚未直接提供 checkbox 的 checked/混合态；样例使用真实分组、编辑属性和独立数据库校验。后续通用观察层应补充这些原始控件事实，业务场景继续负责解释业务含义和预期结果。

## 下一步按业务覆盖推进

| 顺序 | 要交付什么 | 完成标准 |
|---|---|---|
| 先跑稳固定核心套件 | 文本、标签组织、清单父子关系和重启读取；同一源码多轮运行 | 每轮操作、页面证据与数据库结果一致；任何失败保留原结果；报告同时给出耗时和覆盖范围 |
| 补齐架构迁移涉及的业务 | 批量修改、标签改删、任务勾选/重排、附件、备份恢复、目录切换与加密 | 基线和迁移版执行同一业务预期；覆盖正常、异常、取消及重启；独立结果能发现故意引入的业务错误 |
| 固定整个 App 的回归 | 依据 51 功能、143 场景模板、396 展开覆盖槽逐项完成 | 未运行项不消失，环境阻塞单列；固定套件报告成功率、耗时及失败证据。达到完整分母后再判断全 App 的 5～10 分钟目标 |
| 扩展整机回归 | 组合 App 套件，加入权限、系统设置、跨 App 分享、后台恢复及外设 | 固定设备/系统/账号/网络/外设状态；跨 App 与硬件链路有各自独立结果校验 |

不需要先增加一个 Intent→Script 编译器。当前已经可以由 Agent 读取真实记录并写出可运行脚本；优先让来源索引、前置数据、选择器、等待条件和结果校验可复用。只有重复整理成本成为实际瓶颈，再自动生成场景骨架。

## 对速度的判断

固定流程交给 Script 执行是合理的：它省去了每一步等待 Agent 推理和调度的开销。现有成功运行已经给出了秒级实例。业务网络、页面渲染、重启和采集证据仍需要时间，因此应把“整个 App 在 5～10 分钟完成”作为冻结业务范围后的性能目标。

建设脚本的时间与回归时间分别记录。没有实际测量的 Agent/model 耗时保持空值；不能用工具调用时间冒充模型成本，也不能把小套件结果线性放大成整机结论。持续比较的对象应是同一前置状态、相同业务检查与证据要求下的完整套件。

入口：`INTENT_TO_SCRIPT.md` 说明工作流，`SCRIPT_REGRESSION.md` 给出复跑命令，`固定回归结果.md` 和 `测试进度.md` 记录实测与限制，`GPT_PRO_调研补充.md` 可作为外部调研的最新背景。
