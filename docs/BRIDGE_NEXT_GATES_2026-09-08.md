# Bridge 后续关口与范围

本轮复核依据是用户的产品目标、当前源码、[总计划](SCRIPT_INTENT_RUNTIME_CAPTURE_MASTER_PLAN.md)与已保存的真机验证。交付对象始终是 Bridge：Intent 支持日常操作并积累真实证据，Agent 据此编写 Script，Script 在固定前提下连续回归并留下本轮证据。测试脚本和业务预期仍由 Agent 编排。

## 当前已经证明的范围

- NotallyX 提供复杂真实 App、架构迁移和独立业务数据库校验环境。
- 已完成 Intent 搜索探索、冻结证据、独立上下文编写 Script；同一源码在 PGFM10、PKR110 上三次正向、错误期望和等待 Agent 时取消均符合预期。见[跨设备结果](INTENT_SCRIPT_CROSS_DEVICE_2026-09-08.md)。
- 公开 Host 证据导出和离线核验已完成。当前一轮补充显式文件采证，使完整 Script 返回值、断言、截图及已查询的手机载荷可以随包搬移。

这足以支持 Android 主链路继续推进；还不能推导跨 App、全 App、整机回归或全平台交付已经完成。搜索流程耗时不能代替四 App 的固定覆盖范围门禁。

## 接下来按这个顺序推进

1. **本轮收口证据归档。** 仅补真实来源、文件保存、引用关联和离线核验。用已有冻结 Script 验证新增采证不改动作和预期，另用真实 SDK 事件验证手机载荷。保留错误和缺失，不建设常驻 Host 手机数据副本、自动脚本转换或报告系统。
2. **第二个复杂 App。** 沿原计划优先 LocalSend，检验 Flutter 路径与 NotallyX native 路径的差异。固定版本、设备与本地夹具后，先用 Intent 探索已有收发页面、设置与文件选择取消等流程，再交给新上下文编写 Script。要求同源三次复跑、错误预期与取消、独立结果及设置恢复核验。只修暴露的 Bridge 通用缺口；不以完善 LocalSend 产品功能为任务。
3. **可靠性关口。** 对正在执行的设备动作取消、断连、证据淘汰和重启补公开入口试验。本轮观察到的手机无游标历史精确查询超时应归入此处；单独冻结数据规模、查询窗口与延迟，不能由归档文件兜底为成功。等待 Agent 时取消和当前窗口读取不能替代这些证明。
4. **安装与扩展。** 统一开发包、公开能力发现、文档和 Skill，做干净目录安装及真机复现；随后按原四 App 矩阵扩展场景，并补 Python 同义流程和 iOS 实测。先证明各 App 的套件能独立复用，再组合整机回归。

各阶段的收口条件是明确的真实验证结果，不是文档数量、样例 App 功能数量或测试断言总数。只有出现阻断上述关口的实际缺口，才继续增加运行时机制；已有搜索流程不再作为长期扩张任务。

冻结 Intent 证据已交给独立新上下文编写 Script。最终 v1.0.5 在 PGFM10 完成 core、三次同源完整正向、错误设备名和等待控制器时取消；三次完整正向分别为 4 分 46.432 秒、4 分 42.315 秒、3 分 42.386 秒。每次设置变更有独立真实偏好读取，原始设置几何与真正推进的 Flutter 快照也经过独立复核，6 份归档和外部设置证据包均通过离线检查。见 [Script 复用结果与保留失败](LOCALSEND_SCRIPT_REUSE_2026-09-08.md)。这些结果证明当前场景的 UI、控制、外部结果和归档复用能力。

Flutter 动作上下文已继续打通 Android 真机链路。Host/Dart/原生 capture 保留明确动作 ID，公开 Script 新增逻辑坐标 `tap-flutter`。专项固定源码连续三次通过，共核对 12 个真实菜单路由事件及 6 次独立设置变化，错误预期和取消也通过，5 份专项归档和外部证据包可离线核验。Intent 同场景也取得关联的真实路由事实。见 [Flutter 关联结果](LOCALSEND_FLUTTER_ACTION_SCOPE_2026-09-08.md)。
