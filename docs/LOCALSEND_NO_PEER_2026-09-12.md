# LocalSend 空设备场景与控制器收尾

当前 v1.3.0 固定导航场景已在 OPPO `b46093e6` 通过本轮完整执行。公开 start 到观察终态为 **132.939 秒**；148 项断言通过，0 failed、0 inconclusive，31 次动作、338 次调用、14 张截图和 18 页手机采证。完整四 App、iOS 及生产发行仍未完成。此后停止重复这一已通过场景，回到已有 Kiwix 的 Native/H5 业务缺口。

## 这次推进的能力

原场景需要证明空设备分支；此前依赖完整内部 Widget 树，而实际诊断树有深度边界。现在通过新的 Intent 证据和固定上游布局定义主要判定：完整 `flutter-nodes` 中，空文件选择正确；“附近的设备”和“故障排除”完整可见、属于同一顶部滚动容器；它们之间只有一个 46 像素设备图标，没有真实卡片必有的名称或 HTTP/WebRTC 文字。两次符合条件的 SDK 快照必须时间递增、几何匹配，并保存截图。上游 App 和 SDK 均未修改，内部诊断树仍有边界，不再把它当成这一业务结果的必要证据。

网络前提由控制器独立核对：两张 SIM 卡槽都是 ABSENT；只关闭 Wi-Fi；系统没有默认网络或已连接 NetworkAgent，WLAN 为 DOWN 且没有地址。两个空设备检查分别执行 isolate、verify、restore，分别保存 UI 前后网络状态和恢复结果。恢复要求原 Wi-Fi 重新连接，SIM、移动数据和飞行模式值保持原样。手机仍有虚拟接口，所以不能简单要求所有非 loopback 地址消失。此处证明断网条件下的空发现页面，不推断扫描完成或实际传输成功。

详细系统转储保存在带哈希的独立文件，`ctx.askAgent` 回复只带简短结果和引用。Script 仍通过公开 `ctx.call` 观察和操作 App；控制器承担已声明的网络准备，并在失败或取消的 `finally` 中恢复。当前准备过程明确要求无 SIM，不推断其他设备具备同样前提。

初次 Intent 探索保留了两个未通过尝试：01 错把 OPPO 无 SIM 时不变的全局 mobile_data 字段当成禁用结果，02 不能唯一观察正在旋转的刷新图标。两次均恢复网络。刷新不是原固定空发现场景的动作要求，03 直接验证断网后的原业务区域，取得完整节点与截图并恢复 Receive。其 21 条 Intent 记录公开离线验证通过；普通 CLI 节点与截图是单独保存并固定哈希的配套证据，不声称包含在该 Intent 归档附件里。

离线作者检查读取 03 的两份实际节点和 OS 证据，3 个正向条件通过，15 个篡改副本被拒绝，包括设备名称／协议徽章出现、占位图缺失或重复、下方边界不可见、滚动容器不一致、已有选中文件、SIM 可用和网络仍连接。它们不是额外真机运行。
