# 可直接交给实现 agent 的任务：建设美团复杂度的多业务测试 App

这是 AI App Bridge 的大型测试工程，目标是检验效率、能力、故障恢复和调用方自由度。正确性为基础。不要把它收缩成“首页、搜索、商品、购物车、结算”几个通用商城页面，也不要用给相同数据换名字的办法代替真实复杂度。

本提示词可整份交给另一个 agent。开始前读取目标仓库的 AGENTS.md，并核对当前分支、未提交修改、设备和现有测试工程；不覆盖其他人的实验。先提交可审查的页面/状态盘点与实施切片，再持续实现和验证，无需每做一页就等待人批准。

## 目标与三条独立证据线

1. **真实、未接入 SDK 的大型 App**：通过官方渠道安装美团，实际探索各业务入口和动态页面；抖音等应用可补充不同交互模式。使用 Bridge 的 UIA、截图与现有设备命令。记录能做到和做不到的事，不以本地复刻成功替代这条验收。
2. **按真实观察建设的一个大型混合 App**：复现页面结构、信息密度、交互与业务状态的复杂度。交付物是一个安装包。首页和其余页面用 Android View。从已经观察到的业务里挑一条流程，用 Flutter 画在这个 App 里面，由原生页面进入。H5 是这个 App 里的 WebView。从 Native 进入 Flutter 流程、再进入 H5 时带着同一套会话和业务状态。连接自建后端。它必须能独立运行、有真实状态，而不是为测试脚本拼出的演示页面。
3. **可复现的动态压力场景**：在实见机制基础上扩大数据变化、网络时序和故障组合。明确标记合成压力，不冒充美团真实故障。

三类结果分别报告。若只完成其中一条，不能宣布“美团级别验收通过”。本地复刻不连接真实下单或支付服务。

## 登录必须是一套完整会话流程

实现游客浏览、受保护入口触发登录、手机号/账户输入、测试验证码请求与倒计时、验证码错误/过期/重发、协议与长说明中的同名文字、登录成功返回原来页面、登录失败、令牌刷新、会话过期、退出/切换账户。同一个 App 里的 Native 页面、Flutter 流程和 H5 页面共享会话，会话失效对这三处同时生效。

验证码和账户由本地测试服务管理，不发送真实短信；测试凭据通过输入参数或独立测试通道提供。不要把登录按钮直接跳转当登录完成。会话过期后的表单草稿与当前业务上下文应按明确规则保留或失效。

## 后端与请求顺序必须产生真实约束

App 使用真实 HTTP，必要时加 WebSocket/SSE；拥有持久化存储、关联数据、版本和独立审计日志。不能由点击处理器直接显示预定成功文案。

先为每条主要业务链画请求依赖图，区分可并行请求、串行依赖、缓存命中、后台刷新和业务提交。例如首页配置/定位上下文/推荐分块，搜索防抖与游标分页，门店/库存/优惠并行，报价与库存锁定依赖，订单提交、支付处理、状态查询和退款。**这是本地服务合同；只有有抓取证据的第三方请求才标为真实观察，不猜美团私有端点、签名或精确内部时序。**

必须覆盖：

- 请求延迟及分布、抖动、超时、断连、HTTP 错误、部分分块失败、旧请求晚到、取消后响应仍到达。
- 按需重试、刷新游标失效、登录续期、库存/价格版本冲突、报价失效、券状态变化。
- 业务已提交但响应丢失：App 提供查询与恢复，独立账本证明没有重复订单/支付/退款。
- 并发用户/后台参与者改变库存和状态；将“网络成功”“业务成功”“UI 已呈现”分别记录。
- 普通轮询、长连接消息、图片/媒体加载等不影响主业务的在途请求，避免全局 idle 恰好成为测试成功捷径。
- 对错误给可见状态与重试/返回/查询选择，不把一次失败变成无恢复入口的死页。

所有关键请求带本地 `runId`、请求 ID、关联业务 ID、版本与时间；日志记录接收、处理、提交、回包/断开。种子不一定保证线程调度完全相同，因此还要保存实际事件序列和响应摘要，支持失败重现。

## 数据必须真的变化，作者程序不能预知答案

每次运行和刷新产生不同实体集合、店铺/商品/房型/场次、排序、分页边界、图片比例、长短文字、标签、优惠、可用性与价格。实体之间的业务关系保持一致。支持同名不同店、同店不同规格、区域和距离变化、推荐/广告插入、刷新后整批换商家、浏览过程中下架、回到列表后重新排序。

保留用于性能 A/B 的冻结种子，同时提供作者看不到的留出种子。不要只用一个固定成功 seed，也不要只对固定 `S001/P001` 编写脚本。任务以约束描述，例如在当次结果中选满足价格/营业/配送条件的门店，再选可用规格；执行器从可见观察中解析对象。若条件确实无解，应能准确结束并说明，不能悄悄替换成另一个任务。

测试脚本不得调用服务端内部查询接口获取目标答案、直接写订单或绕过 UI 完成业务。独立验收器可以读取账本和事件日志，但必须与执行器分离。

## 页面实现要具有实际操作难度

- 接近实见页面的信息密度、嵌套滚动、固定栏、复杂卡片、重复文字、长说明、半屏/全屏弹层、图片和异步占位；不能全是稀疏按钮表单。
- Native 页面、Flutter 流程和 H5 页面都在这一个 App 里实际绘制。Flutter 只承担一条业务流程，H5 只承担 WebView 页面。三者带着同一套会话和业务状态。Flutter 和 H5 都不要再做成可以单独安装的应用，也不要用同一张网页换标题冒充。
- 数据存在、控件可交互、业务数据加载完成、业务结果确认、画面绘制完成，是不同状态。不要靠固定长 sleep 掩盖未实现的状态。
- 使用正常可访问性语义；可以增加明确标记的可访问性差/Canvas/纯图形压力页，但不能让整个测试集为 Bridge 定制独有答案属性。
- 常见误触与恢复要自然发生：按钮在滚动后移动、对象在观察后替换、对话框关闭、键盘遮挡、网络失败后保留表单、返回后恢复列表位置。

## 验收方式与禁止的捷径

先交页面地图、状态图、网络图、数据/故障模型与一个纵向可运行切片；随后按多个业务域扩展到盘点范围，持续运行完整流程。第一片切片不是最终交付。

验收至少包括：

1. 已知页面/信息足够后的 Intent 或普通 JS/Python Script 连续执行；单次外部提交可覆盖完整业务分支，不强迫回模型。
2. 陌生数据的观察、选择、分页、分支和恢复；种子在作者源码冻结后选择。保存所有失败，不能只报成功或最快样本。
3. 同一个 App 内从 Native 进入 Flutter 流程再进入 H5、跨业务订单、会话失效、多层弹窗、回包丢失、进程重启、取消后显式继续、重复确认、数据冲突。
4. 独立账本与 UI/请求证据相互核验：选的是满足本次任务条件的实体，数量/价格/优惠/库存/状态准确，未知作用没有被自动重放。
5. 同源码/同业务条件的交错 A/B。分别报告编写/首次探索、工具执行、真实网络/动画等待、恢复、证据就绪时间、命令/模型回合与输出量。
6. 官方美团这条没有接入本 SDK 的结果单独报告通过率、耗时、缺失能力和误报。本地这一个测试 App 接入 SDK，交付这一份安装包。
7. 后端、客户端、测试作者、验收器之间不能共享隐藏的正确目标或预定成功状态；不能用直接 API 写入代替 UI。

不要求“一分钟遍历整个美团所有页面”这种无明确覆盖口径的数字。验收目标是预先声明的复杂流程在信息足够后尽可能快、连续、正确，出错后能继续；不靠删动作、删断言、改小数据或隐藏恢复成本提速。
