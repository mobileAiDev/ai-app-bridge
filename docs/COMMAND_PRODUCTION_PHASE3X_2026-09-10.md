# 第三阶段 X：iOS 历史查询扫描成本

## 当前结论

已修复两处实际浪费：C 全局扫描逐条重读段前缀，及 iOS 采证查询读取无关分区。四个 3W 原引用均从同一 iPhone 的原数据容器恢复，原始载荷和引用不变。**历史精确查找的性能关口仍未完成**：状态/事件共享分区还需要按页扫描，下一步是有界、可冷恢复的原引用位置索引。

本轮未修改样例 App 业务源码，未清理或重写旧证据。Android 3O 固定矩阵未重跑；iOS/Web Intent/Script 仍关闭，整体生产验收未完成。

## 代码修改

1. `candidate_in_partition` 现在保留已校验的读取位置；每分区三个 UInt64，共八个分区。游标回退、淘汰和冷重开仍从当前分段元数据确定位置，不保存载荷或查询结果。
2. C 分区游标支持只给 `after_sequence`、物理地址为零的定位。成功后返回物理游标；失败、容量不足和 EOF 不推进游标。已越过被淘汰前缀的请求，不把其他分区的序列空隙当成丢证。磁盘格式、原序列和引用未修改。
3. iOS `SegmentedCaptureBackend` 按实际存储分区读取：日志 2、网络 0、状态/事件 4。页的全局序列上界、1024 条扫描限制、字节/时间预算和原载荷校验保留。Swift/C 的 Flutter 镜像同步。
4. 干净安装检查发现三项 Web 负向用例仍未提供已要求的 `runtimeEpoch`，已补齐。原有“无效参数不得分派设备/程序操作”的断言保留；未改变 Web 产品合同来迁就检查。
